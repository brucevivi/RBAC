1. Why Do We Need Authentication & Authorization At All?

Think of a hotel.
When you arrive, you go to the front desk (login). They check your ID and give you a key card (token).
The key card opens your room (resource A) but not the presidential suite (resource B).
You don't show your ID card every time you open a door — you just tap the card.
The card expires at checkout time. If you want to stay longer, you go back to the desk (refresh token).

Authentication = showing your ID at the front desk (who are you?)
Authorization = the key card deciding which doors open (what can you do?)
Token = the key card itself

In our SiprotecV system, many people use the substation server:

  • Operators — can view live data and control breakers
  • Engineers — can configure devices and upload firmware
  • Auditors — can only read logs

Every HTTP request to the server must answer two questions:

Authentication (AuthN) vs Authorization (AuthZ)

QuestionWho are you?What are you allowed to do?
AnswerI am Alice, user ID abc-123Alice has role Engineer, which allows write:config

Username + password alone answers AuthN but gives no structured answer to AuthZ, and doesn't work across multiple microservices. That's the gap OAuth2, OIDC, and RBAC fill.

What Is OAuth2?

Valet parking.
You give the valet a valet key (access token), not your master key. The valet key can start the engine and drive, but can't open the trunk or glove box. You've delegated limited access without sharing your full credentials.

🔑   OAuth2 = Delegated Authorization   🔑

"I, the user, delegate my authority to this app — but only limited authority, for a limited time, without sharing my password."

OAuth literally stands for Open Authorization.
The entire protocol is one idea: delegate access without sharing credentials.

Without OAuth2:"Here's my password, do whatever you want."
With OAuth2:"Here's a temporary pass. It lets you read my data for 1 hour. That's it."

OAuth2 in plain English: Instead of giving every app your password, you log in once at a trusted server (Hydra). That server gives the app a temporary pass (access token). The app shows that pass to APIs. The pass expires. Nobody ever sees your password.

That's it. Three steps:

1. You prove who you are        → (username + password → Hydra)
2. Hydra gives the app a pass   → (access token, 1 hour)
3. App shows the pass to APIs   → (Bearer token in every request)

The Four Actors (in simple terms)

WhoPlain EnglishIn our system
You (Resource Owner)The human who owns the dataThe operator / engineer using the browser
The App (Client)The software asking for data on your behalfAngular frontend (SiprotecV)
The Gatekeeper (Authorization Server)The trusted server that checks your password and issues passesOry Hydra
The Data (Resource Server)The APIs that have the actual databay-data-aggregator, bay-manager, etc.
Why not just send username+password with every API call?
  • Every microservice would need to validate credentials — duplicated logic, security risk
  • Credentials sent on every request — wider attack surface
  • No concept of scope (what the app can access on your behalf)
  • No expiry — if intercepted, attacker has permanent access
  • Password change requires re-login everywhere simultaneously

OAuth2 solves all of these. Password is used exactly once. Everything after that uses short-lived tokens.

What Is OIDC (OpenID Connect)?

OAuth2 gives you a valet key. OIDC adds a name badge.
The valet key (access token) lets you park the car but says nothing about who you are. OIDC adds a name badge (ID token) that says "I am Alice, room 42, VIP guest."

OIDC = OAuth2 + Identity. It adds two things on top of OAuth2:

  1. The id_token — a JWT containing claims about the user (name, email, roles, subject ID)
  2. Standard endpoints — so any client can discover how to talk to any OIDC server (the Discovery Document)

OAuth2 vs OIDC — What's the Actual Difference?

This confuses almost everyone. Here's the simplest way to think about it:

OAuth2 is the building. OIDC is one specific floor inside it.

Imagine a 10-story office building (OAuth2). Each floor has different offices (grant types, scopes, token types). OIDC is Floor 3 — the Identity Department. It uses the building's elevators (authorization code flow), the building's mailroom (token endpoint), and the building's security desk (client_id check). But it adds its own department: an identity counter (userinfo endpoint) and a name badge printer (id_token).

You can use the building (OAuth2) without ever visiting Floor 3 (OIDC) — for example, machine-to-machine API calls don't need to know "who" is calling, just "is this call allowed?" But if you need to know who someone is, you go to Floor 3.

The One-Line Summary

OAuth2 answers: "Is this app allowed to access this data?"
OIDC answers: "Is this app allowed to access this data?" + "WHO is the human behind this app?"

How to remember it
  • OAuth2 = the plumbing (pipes, valves, water flow) — it moves tokens around
  • OIDC = the shower head on top — it gives you something useful (user identity) using that plumbing
  • You can't have OIDC without OAuth2 (no shower without pipes)
  • You CAN have OAuth2 without OIDC (pipes without a shower — useful for machine-to-machine flows)
  • In our CPC system, we always use both, because we always need to know who the user is (for RBAC)

⚠️ The Subtle Truth — AuthN Happens First, But...

🔒 Step 1: Authentication DOES happen. The user MUST prove identity (username + password) before OAuth2 issues anything. No valid user → no access token. You're right about this.
🔑 Step 2: But the access token only carries authZ. Once the user proves identity, the access token that comes out says "this request is allowed, roles = [Engineer]" — but NOT "this is Alice, email alice@grid.com." The identity info is not in the access token.
🪪 Step 3: OIDC adds the identity. The id_token is the one that carries "this is Alice, alice@grid.com, Engineer." That's the authN proof that the frontend can read.

🏪 Analogy: A bouncer at a members-only store

OAuth2: The bouncer (Grid Identity) checks your ID at the door (authentication). If you're valid, he gives you a shopping pass (access token) that says "Section A: allowed, Section B: not allowed." But the pass doesn't have your name or photo on it — it's just a permission slip.

OIDC: Same bouncer, same check. But now he also gives you a name badge (id_token) that says "Alice, VIP Member." The shop assistant reads the badge to say "Welcome, Alice!" — but the doors still only care about the shopping pass.

The key: AuthN (checking your ID) is a prerequisite for getting any token. But the access token itself only carries permissions (authZ), not identity (authN). The id_token carries identity.

So to be precise:
❌ "OAuth2 does authN + authZ" — not quite
❌ "OAuth2 only does authZ, no authN involved" — also not quite
✅ "OAuth2 requires authN as a prerequisite, but the token it issues only carries authZ. OIDC adds authN proof (id_token) to the output."

What Is RBAC (Role-Based Access Control)?

Hospital badges.
Dr. Smith has a "Doctor" badge → can enter surgery rooms, prescribe medication.
Nurse Jones has a "Nurse" badge → can enter patient rooms, administer medication.
Visitor has a "Visitor" badge → can enter the lobby only.
You don't set permissions per person — you set them per role, then assign roles to people. 
User "Alice"  →  Role "Engineer"  →  Permissions: [read:data, write:config, upload:firmware]
User "Bob"    →  Role "Operator"  →  Permissions: [read:data, write:control]
User "Carol"  →  Role "Auditor"   →  Permissions: [read:data, read:logs]

2. Tokens — The Currency of Authentication

After login, the user gets three tokens. Think of them as three different keys:

Access Token (JWT)

A boarding pass.
It has your name, flight number, seat, gate, and a barcode. The gate agent scans the barcode (verifies the signature) — they don't call the airline to confirm. It's self-contained. And it expires when the flight departs.

A JWT (JSON Web Token) has three Base64-encoded parts separated by dots:

eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c2VyMTIzIiwicm9sZXMiOlsiRW5naW5lZXIiXX0.[signature]
 ──── HEADER ────        ────────── PAYLOAD ───────────────────────       ── SIG ──
Click to see what's inside each part

Header — tells you the algorithm used to sign:

{
  "alg": "RS256",        // RSA + SHA-256 signature
  "typ": "JWT",
  "kid": "hydra-key-1"   // which key was used (matches JWKS)
}

Payload — the actual claims (data):

{
  "iss": "http://192.168.1.10:8000/api/v1/auth",  // issuer — WHO signed this
  "sub": "user-uuid-abc123",                       // subject — WHO this is about
  "exp": 1716003600,                               // expiry — WHEN it dies
  "iat": 1716000000,                               // issued at
  "jti": "token-uuid-xyz",                         // unique token ID
  "scope": "openid offline",                       // what was requested
  "client_id": "cpc-frontend",                     // which app requested it
  "ext": {
    "roles": ["Engineer"]                           // ← injected by token hook
  }
}

Signature — proves nobody tampered with it:

RSA_SHA256(
  base64(header) + "." + base64(payload),
  hydra_private_key    // only Hydra has this
)

Anyone with Hydra's public key can verify the signature. But only Hydra (with the private key) can create valid signatures.

Key Property — Stateless
The token carries all the info needed to validate it. No microservice needs to call Hydra to check "is this token valid?" — they just verify the signature with Hydra's public key, check expiry, and read the roles. This is why JWTs scale so well.

Lifetime: 1 hour (configured in hydra.yml: ttl.access_token: "1h")

ID Token

Also a JWT, but intended only for the frontend — never sent to APIs. Contains human-readable identity info:

{
  "iss": "http://192.168.1.10:8000/api/v1/auth",
  "sub": "user-uuid-abc123",
  "aud": "cpc-frontend",         // audience — this token is FOR this client
  "nonce": "random123",          // CSRF protection (must match what was sent)
  "name": "Alice Engineer",
  "email": "alice@grid.com",
  "roles": ["Engineer"]
}

The Angular app reads this to display "Welcome, Alice" in the UI. It is never sent as a Bearer token to APIs.

Refresh Token

A season pass renewal card.
Your day pass (access token) expires every day. Instead of buying a new pass (logging in again), you show your renewal card (refresh token) and they give you a fresh day pass. The renewal card works for a whole season (30 days). When you use it, they give you a new renewal card too (rotation) — so the old one can't be reused if stolen.

Why needed? The access token expires in 1 hour. Without a refresh token, the user would be forced to log in again every hour. With it, the frontend silently exchanges the refresh token for a new access token — the user never notices.

Refresh token: ory_rt_abc123xyz....

NOT a JWT. It's an opaque string.
Stored in Hydra's PostgreSQL database.
Maps to: subject, client_id, scopes, expiry (720h = 30 days)
One-time-use: rotated on every use (old one invalidated)

Lifetime: 720 hours = 30 days (ttl.refresh_token: "720h")

YES — refresh token renews BOTH access token AND id token

  • If the original login only requested scope=offline (no openid), then refresh gives you: new access_token + new refresh_token — NO id_token
  • In our CPC system, we always request openid offline, so we always get all three renewed.

3. PKCE — Proof Key for Code Exchange

A sealed envelope with a secret code.
  1. You write a secret word on a paper ("dBjftJeZ4CVP") — this is the code_verifier
  2. You put the paper in a sealed envelope (hash it) — this is the code_challenge
  3. You give the sealed envelope to the bank (Hydra) with your loan application (auth request)
  4. The bank processes your application and gives you a claim ticket (auth code)
  5. If someone steals your claim ticket, they can't collect the money because they don't know the secret word
  6. When you come to collect, you show the original paper with the secret word (code_verifier). The bank opens the envelope and checks: does SHA256("dBjftJeZ4CVP") match? Yes → here's your money (tokens)

4. The Discovery Document

Instead of hardcoding all of Hydra's endpoint URLs, any OIDC client can fetch a single well-known URL and discover everything automatically:

GET http://192.168.1.10:8000/api/v1/auth/.well-known/openid-configuration

Hydra returns a JSON document like:

{
  "issuer": "http://192.168.1.10:8000/api/v1/auth",
  "authorization_endpoint": "http://192.168.1.10:8000/api/v1/auth/oauth2/auth",
  "token_endpoint": "http://192.168.1.10:8000/api/v1/auth/oauth2/token",
  "jwks_uri": "http://192.168.1.10:8000/api/v1/auth/.well-known/jwks.json",
  "userinfo_endpoint": "http://192.168.1.10:8000/api/v1/auth/userinfo",
  "end_session_endpoint": "http://192.168.1.10:8000/api/v1/auth/oauth2/sessions/logout",
  "scopes_supported": ["openid", "offline", "profile"],
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token", "client_credentials"],
  "code_challenge_methods_supported": ["S256"]
}
Why this matters
The frontend is self-configuring. Change the issuer URL and all endpoints follow.
But wait — how does Angular know the issuer URL in the first place?

This is a chicken-and-egg problem:

  • Angular needs to fetch the discovery doc to know all the OIDC endpoints
  • To fetch the discovery doc, Angular needs the issuer URL
  • But the issuer URL contains the server IP (e.g. http://192.168.1.10:8000/api/v1/auth), which changes per deployment
  • Angular can't hardcode it — it's different on every substation

The solution: /api/v1/client-config.json

The oidc-proxy (nginx) serves a tiny JSON file that contains just one thing — the issuer URL for this specific deployment:

// Angular's FIRST network call after loading:
GET /api/v1/client-config.json

// Response (served by oidc-proxy from a Kubernetes ConfigMap):
{
  "oidcAuthority": "http://192.168.1.10:8000/api/v1/auth"
}

// Now Angular knows the issuer! It fetches:
GET http://192.168.1.10:8000/api/v1/auth/.well-known/openid-configuration
// … and discovers ALL other endpoints automatically.

Where does the ConfigMap come from? The Domain Detector Job runs at deploy time, discovers the server’s IP, and writes it into the oidc-client-config ConfigMap. The oidc-proxy reads this ConfigMap and serves it as client-config.json.

Chain: Domain Detector (discovers IP) → ConfigMap oidc-client-config → oidc-proxy (serves it) → Angular (reads it) → fetches discovery doc → knows all endpoints.

5. The Issuer — The Trust Anchor

The issuer is like the name of the bank printed on a banknote.
If a $100 bill says "Federal Reserve" on it, and your shop only accepts Federal Reserve notes, you check that the name matches. If someone hands you a note printed by "Bob's Garage Bank," you reject it — even if it looks real — because it's from an untrusted issuer.

The issuer URL is the canonical identity of the authorization server. It appears in:

  • The iss claim inside every JWT token Hydra issues
  • The discovery document
  • The security-service's Authority configuration

When security-service validates a token, it checks:

Step 1: Does the signature verify?      (using JWKS public key)
Step 2: Is the token expired?            (check exp claim)
Step 3: Does iss == configured Authority? ← THIS IS THE CRITICAL CHECK
        "http://192.168.1.10:8000/api/v1/auth" == "http://192.168.1.10:8000/api/v1/auth"?
        YES → proceed
        NO  → 401 Unauthorized (reject the token entirely)
Why iss check is a security requirement
Without the iss check, an attacker could set up their own OIDC server, issue a JWT with roles: ["Admin"], and your system would accept it. The iss check ensures: "I only trust tokens signed by the SPECIFIC server I was configured to trust."

7. redirect_uri — What It Really Means

A return address on a letter.
When you send a letter (auth request) to the tax office (Hydra), you write a return address (redirect_uri) on the envelope. The tax office sends the reply (auth code) to that address. But the tax office first checks: "Is this return address on our approved list for this person?" If not, they shred the letter. This prevents someone from registering YOUR request with THEIR return address.

The redirect_uri is the URL where Hydra sends the user back after they've logged in, carrying the auth code.

Browser → Hydra: "Here's a login request, send the result to http://192.168.1.10:8000/callback"
Hydra checks:    "Is http://192.168.1.10:8000/callback in the registered redirect_uris for this client?"
                  YES → proceed, send auth code to that URL
                  NO  → reject immediately ("redirect_uri mismatch")
This is why IP changes break login
redirect_uri was registered as http://192.168.1.10:8000/callback. If the IP changes to .50, the browser sends http://192.168.1.50:8000/callback. Hydra says "that's not registered" → login fails. This is a security feature, not a bug.

🪝 What is the Token Hook and why is it critical?

The problem: Hydra is a generic OAuth2 server. It knows how to issue tokens, but it has no idea what roles a user has. Hydra doesn't store users or roles — Grid Identity does (in PostgreSQL). So how do roles end up inside the JWT?

The solution — Token Hook: Hydra has a feature where, right before it signs and issues a token, it makes an HTTP call to an external service and says: "I'm about to issue a token for user X. Do you want to add anything to it?"

How it works step by step:

1. User logs in successfully → Hydra is about to issue tokens

2. BEFORE signing the JWT, Hydra calls the token hook:
   POST http://grid-identity:3500/api/v1/token/hooks
   Body: { "subject": "user-uuid-abc123", "client_id": "cpc-frontend", ... }

3. Grid Identity receives this, looks up the user in PostgreSQL:
   SELECT roles FROM user_roles WHERE user_id = 'user-uuid-abc123'
   → result: ["Engineer"]

4. Grid Identity responds:
   { "session": { "access_token": { "roles": ["Engineer"] } } }

5. Hydra takes that response and MERGES it into the JWT payload:
   {
     "sub": "user-uuid-abc123",
     "ext": {
       "roles": ["Engineer"]    ← THIS came from the token hook
     }
   }

6. Hydra signs the JWT with its RSA private key → done.

Why it's critical:

  • Without the token hook → the access token would have NO roles → security-service can't do RBAC → every request would be rejected or everyone would have the same access
  • With the token hook → every token carries the user's roles → security-service reads ext.roles and decides: "Engineer can access /api/bay-data but not /api/admin"
  • The hook also fires on refresh — so if an admin changes a user's role from Engineer to Operator, the new role appears in the next refreshed token (within ~1 hour max)

Configured in hydra.yml:

oauth2:
  token_hook:
    url: http://grid-identity:3500/api/v1/token/hooks

If this URL is wrong or Grid Identity is down, Hydra cannot issue tokens — login fails completely.

11. OIDC Proxy — Why It Exists

A translator at an embassy.
You speak English (localhost:4200). The embassy staff only speak French (real-domain.com). The translator (oidc-proxy) sits in the middle. When you say something, they translate to French and relay it. When the embassy responds in French, they translate back to English for you. Neither side needs to know the other's language.

The Problem

When a developer opens the app at http://localhost:4200, OIDC breaks because:

  • Browser sends redirect_uri=http://localhost:4200/callback — not registered in Hydra!
  • Hydra's issuer is http://192.168.1.10:8000/api/v1/auth — doesn't match localhost
  • Hydra's 302 redirect points to 192.168.1.10 — browser can't reach it from localhost

The Solution

The oidc-proxy (nginx + njs) intercepts only localhost and raw-IP requests:

# Traefik IngressRoute match rule:
(Host(`localhost`) || HostRegexp(`^(\d{1,3}\.){3}\d{1,3}$`))
  && (PathPrefix(`/api/v1/auth/`) || PathPrefix(`/grid-identity/auth/`))

It rewrites redirect_uri on the way in (localhost → real domain) and rewrites Location headers on the way back (real domain → localhost). Real domain traffic bypasses it entirely.

12. Traefik Ingress Controller

The single entry point for all HTTP traffic into the Kubernetes cluster. Routes requests to the correct backend based on URL path. Enforces authentication via the global-auth ForwardAuth middleware.

13. Domain Detector Job

A Kubernetes Job that runs at deploy time and auto-discovers the server's external domain/IP. It checks 4 sources in priority order:

  1. OVERRIDE_DOMAIN (Zarf variable) — explicit, set by operator during deployment
  2. Node annotation vmoperator.siemens.com/server_url — set by VM infrastructure
  3. Traefik LoadBalancer IP — from the Traefik service's external IP
  4. Node InternalIP — fallback, always available (the raw IP address)

Result is written into ConfigMaps external-endpoint-config and oidc-client-config.

Appendix A — Glossary

TermDefinition
OAuth2Protocol to delegate resource access without sharing passwords. Defines actors (client, AS, RS, owner) and grant types (authorization_code, refresh_token, client_credentials).
OIDCOpenID Connect. OAuth2 + identity layer. Adds id_token (who you are) and discovery document (standard endpoints).
RBACRole-Based Access Control. Assign permissions to roles, roles to users. Enforced by security-service on every request.
JWTJSON Web Token. Base64-encoded header.payload.signature. Self-contained, stateless credential.
Access TokenJWT sent as Bearer header on API calls. Contains iss, sub, exp, roles. Verified by security-service. 1h lifetime.
ID TokenJWT for the frontend only. Contains user identity (name, email). Never sent to APIs.
Refresh TokenOpaque string stored in Hydra DB. Exchanged for new access_token silently. 30-day lifetime. One-time use (rotated).
PKCEProof Key for Code Exchange. Random verifier → SHA256 → challenge. Prevents auth code interception. Used with public clients.
IssuerThe canonical URL of the Authorization Server. Appears in every JWT as iss. Trust anchor — validators reject tokens from unexpected issuers.
Discovery DocumentJSON at /.well-known/openid-configuration. Lists all OIDC endpoint URLs. Clients auto-configure from it.
Client IDIdentifies the application (not the user) to Hydra. Hydra checks redirect_uri, scopes, and grant types against the client registration.
Client SecretServer-side credential for confidential clients. Browser never sees it. Used during token exchange.
redirect_uriURL where Hydra sends the user back after login, carrying the auth code. Must exactly match a pre-registered URL.
JWKSJSON Web Key Set. Hydra's public keys at /.well-known/jwks.json. Used by anyone to verify JWT signatures.
ForwardAuthTraefik pattern. Before forwarding a request, Traefik calls security-service to validate the JWT. 200 → forward. 401/403 → reject.
Ory HydraOpen-source OAuth2/OIDC Authorization Server. Issues tokens. Delegates login/consent to Grid Identity.
Grid IdentityASP.NET Core service. Hydra's login provider. Validates credentials. Manages users/roles in PostgreSQL. Token hook injects roles.
security-serviceASP.NET Core service. ForwardAuth JWT validator. RBAC enforcer. Certificate manager. OIDC client creator.
oidc-proxynginx + njs. Fixes OIDC when accessing via localhost or raw IP. Rewrites redirect_uri and Location headers.
BFFBackend For Frontend. The IDP Wrapper service that mediates between browser and Grid Identity/Hydra.
domain-detectorKubernetes Job. Auto-discovers external domain/IP at deploy time. Writes ConfigMaps.
Token HookHydra calls Grid Identity before issuing a token. GI injects user roles into the JWT payload.
CSRF Cookieory_hydra_login_csrf_<hash>. Set by Hydra. Must be present during login. Prevents cross-site request forgery.
